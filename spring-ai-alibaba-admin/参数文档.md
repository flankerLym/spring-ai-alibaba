# Spring AI Alibaba Admin 开放 API 联调文档

> 面向对象：下游 B 端系统 / 第三方企业系统

---

## 1. 接入说明

### 1.1 Base URL

实际域名或 IP 由服务提供方分配，这里统一使用：

```text
https://{host}
```

### 1.2 鉴权方式

所有 `/api/v1/**` 开放接口均需要 API Key 鉴权。

请求头：

```http
Authorization: Bearer <API_KEY>
Content-Type: application/json
```

示例：

```http
Authorization: Bearer sk-xxxxxxxxxxxxxxxx
```

API Key 无效时 HTTP 状态码为 `401`，返回示例：

```json
{
  "request_id": "8f47f6d5xxxxxxxx",
  "code": 401,
  "message": "Api key is invalid."
}
```

## 2. 接口总览

| 功能 | Method | Path | 返回方式 |
|---|---|---|---|
| 查询已发布应用及入参 Schema | GET | `/api/v1/apps/published` | JSON |
| Workflow 同步调用 | POST | `/api/v1/apps/workflow/completions` | JSON / SSE |
| Workflow 异步启动 | POST | `/api/v1/apps/workflow/async-completions` | JSON |
| Workflow 异步结果查询 | POST | `/api/v1/apps/workflow/async-results` | JSON |
| Workflow 异步任务停止 | POST | `/api/v1/apps/workflow/stop-completions` | JSON |

# 4. Workflow 同步调用

## 4.1 接口

```http
POST /api/v1/apps/workflow/completions
```

支持：

- `stream=false`：同步 JSON 返回
- `stream=true`：SSE 节点级流式返回

---

## 5.2 请求参数（示例）

```json
{
  "app_id": "2101945275265347585",
  "conversation_id": "2102324804131487745",
  "stream": true,
  "draft": false,
  "input_params": [
    {
      "key": "query",
      "type": "String",
      "source": "sys",
      "value": "我是抑郁了"
    },
    {
      "key": "tk_sn",
      "type": "String",
      "source": "user",
      "value": "1234"
    },
    {
      "key": "tk_phone",
      "type": "String",
      "source": "user",
      "value": "13800138000"
    }
  ]
}
```

### 顶层字段

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---:|---|---|
| `app_id` | String | 是 | - | Workflow 应用 ID |
| `conversation_id` | String | 否 | 服务端生成 | 会话 ID |
| `request_id` | String | 否 | 服务端生成 | DTO 支持该字段，但外部调用不建议传 |
| `messages` | Array | 否 | - | 历史消息，可作为 Workflow 上下文 |
| `stream` | Boolean | 否 | `false` | 是否启用 SSE |
| `draft` | Boolean | 否 | `false` | 是否使用草稿；B 端建议固定 false |
| `input_params` | Array | 建议必传 | - | Workflow 入参 |

---

## 5.3 `input_params[]`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `key` | String | 是 | 参数名 |
| `type` | String | 是 | 参数类型 |
| `source` | String | 是 | `sys` 或 `user` |
| `value` | Any | 是 | 实际参数值 |
| `desc` | String | 否 | 参数描述 |
| `value_from` | String | 否 | 值来源描述 |
| `required` | Boolean | 否 | 是否必填 |
| `default_value` | Any | 否 | 默认值 |

### 常用 `source`

#### `sys`

系统变量，例如：

```json
{
  "key": "query",
  "type": "String",
  "source": "sys",
  "value": "用户输入的问题"
}
```

#### `user`

Workflow Start 节点配置的业务入参，例如：

```json
{
  "key": "order_no",
  "type": "String",
  "source": "user",
  "value": "ORDER202609230001"
}
```

> Workflow 的自定义参数以 `/api/v1/apps/published` 返回的 `inputSchema` 为准。



# 10. 错误结构

项目中存在两种主要错误返回格式。

## 10.1 同步 Chat / Workflow 错误对象

```json
{
  "status_code": 400,
  "type": "invalid_request_error",
  "code": "MissingParameter",
  "message": "Required parameters [appId] missing, please check the request parameters.",
  "param": "app_id"
}
```

字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status_code` | Integer | HTTP/业务状态码 |
| `type` | String | 错误类型 |
| `code` | String | 业务错误码 |
| `message` | String | 错误信息 |
| `param` | String | 出错参数，可能不返回 |

## 10.2 `Result<T>` 接口错误

异步启动、结果查询、停止、已发布应用查询等接口使用：

```json
{
  "request_id": "req_xxx",
  "code": 400,
  "message": "Workflow config is invalid, taskId not exists"
}
```

> 对 `Result<T>` 类型接口，调用方不要只判断 HTTP Status，还必须判断响应 Body 中的 `code` 是否为 `200`。

---

# 11. 常见错误码

| HTTP / code | 业务 Code | 说明 |
|---:|---|---|
| 400 | `MissingParameter` | 缺少必填参数 |
| 400 | `InvalidParameter` | 参数格式非法 |
| 400 | `AppNotPublished` | 应用尚未发布 |
| 400 | `WorkflowConfigInvalid` | Workflow 配置或 task_id 无效 |
| 401 | `InvalidApiKey` | API Key 无效 |
| 404 | `AppNotFound` | 应用不存在 |
| 500 | `WorkflowExecuteError` | Workflow 执行失败 |
| 500 | `WorkflowGetDebugProcessError` | Workflow 异步结果获取失败 |
| 503 | `WorkflowExecuteTimeout` | Workflow 执行超时 |

# 12. B 端推荐调用流程

## 12.1 Chat

```text
1. 服务提供方分配 API_KEY
        ↓
2. GET /api/v1/apps/published
        ↓
3. 获取 BASIC 应用 app_id
        ↓
4. POST /api/v1/apps/chat/completions
        ↓
5. 保存 conversation_id
        ↓
6. 后续多轮对话继续传 conversation_id
```

## 12.2 Workflow 同步

```text
1. GET /api/v1/apps/published
        ↓
2. 获取 Workflow app_id + inputSchema
        ↓
3. 按 Schema 组装 input_params
        ↓
4. POST /workflow/completions
        ↓
5. 读取 message.content
```

## 12.3 Workflow 异步

```text
POST /workflow/async-completions
        ↓
获取 task_id
        ↓
POST /workflow/async-results
        ↓
task_status = executing → 继续轮询
        ↓
task_status = success / fail / pause / stop → 停止轮询
```

# 13. 联调注意事项

1. **所有 `/api/v1/**` 接口均需要 `Authorization: Bearer <API_KEY>`。**

2. **B 端只能稳定依赖已发布版本。**  
   Chat 的 `is_draft` 和 Workflow 的 `draft` 建议固定不传或传 `false`。

3. **Workflow 自定义参数不是固定字段。**  
   应以应用发布后的 Start 节点参数为准，可通过 `/api/v1/apps/published` 的 `inputSchema` 获取。

4. **Workflow 的 `query` 参数属于 `sys` 参数。**

```json
{
  "key": "query",
  "type": "String",
  "source": "sys",
  "value": "用户问题"
}
```

5. **Start 节点业务变量使用 `source=user`。**

6. **SSE 没有 `[DONE]` 终止标识。**  
   请根据 `status=completed` / `failed` 判断业务结束，同时监听连接关闭。

7. **Workflow SSE 的 `message.content` 是增量片段。**  
   下游需按事件顺序拼接。

8. **同步 Workflow 的 `message.content` 来自 End 节点汇总。**  
   如果 End 节点输出的是 JSON 字符串，下游需要再次做 JSON 解析。

9. **不要仅根据 HTTP 200 判断业务成功。**  
   同步响应需要检查 `error`；`Result<T>` 响应需要检查 `code`。

10. **字段值为 null 时服务端通常不会序列化该字段。**  
    下游解析时不要依赖所有可选字段一定存在。

11. 建议下游在日志中保存：

```text
request_id
trace_id（如有）
conversation_id
task_id（Workflow）
app_id
HTTP status
业务 code
```

便于双方快速定位链路问题。

# 15. 最小联调 Checklist

首次联调时建议依次确认：

```text
[ ] API Key 是否有效
[ ] GET /api/v1/apps/published 是否成功
[ ] app_id 是否为已发布应用
[ ] Workflow input_params 是否与 inputSchema 一致
[ ] source 是否正确使用 sys / user
[ ] Content-Type 是否为 application/json
[ ] SSE 客户端是否关闭代理缓冲
[ ] 是否正确保存 conversation_id / task_id
[ ] 是否同时判断 HTTP 状态与业务 error/code
[ ] 日志中是否保留 request_id
```
